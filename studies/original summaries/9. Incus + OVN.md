### Visão geral sobre o Incus

O Incus é uma plataforma de gerenciamento de containers e VMs. Ele é um fork derivado do LXD e fornece uma API e uma CLI para você administrar uma infraestrutura de computação. Então por exemplo, ao invés de fazer manualmente comandos como: 

``` 
criar VM
configurar disco
configurar CPU
criar interface
configurar rede
configurar IP
configurar DNS
```

Basta fazer:
`incus launch images:ubuntu/24.04 vm1`
E o Incus coordena a criação da instância e dos recursos necessários.

O Incus possui os seguintes mecanismos em sua arquitetura:
- `incus` (CLI, Go): Fala REST/HTTP com o daemon, por socket unix `/var/lib/incus/unix.socket` ou HTTPS (:8443) com autenticação por certificado.
- `incusd` (daemon, Go): Contém tudo - Gerenciamento de instâncias (LXC para containers de sistema, QEMU para VMs), storage drivers, network drivers, devices e o banco de custer (Cowsql/dqlite, SQLite replicado via RAFT)
- Network drivers: Disponíveis em `internal/server/network/`- `bridge`, `ovn`, `physical`, `macvlan`, `sriov`O driver `ovn` é o `driver_ovn.go`.
- Devices drivers: Disponíveis em `internal/server/device/`- `nic_bridged`, `nic_ovn`, `nic_p2p`, `nic_routed`, `nic_sriov`, `nic_physical`, `nic_macvlan`, `nic_ipvlan`.

Essa é a arquitetura conceitual de como o Incus funciona:

                 Usuário
                    │
                    ▼
             incus CLI
                    │
                    ▼
              Incus API
                    │
                    ▼
              Incus daemon
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
      Storage      CPU        Network
        │                       │
        │                       ▼
        │                  OVN / OVS
        │
        ▼
    Container/VM

O Incus pode ser utilizado para montar algo que funciona como uma private cloud, principlamente para ambientes de infraestrutura/virtualização. Por exemplo:
                  Incus Cluster
        ┌────────────────────────────┐
        │                                                   │
        │   Incus Server 1                          │
        │   Incus Server 2                          │
        │   Incus Server 3                          │
        │                                                   │
        └────────────────────────────┘
             │           │             │
            ▼          ▼            ▼
            VMs    VMs     Containers

O cluster Incus possui uma base de dados distribuída baseada em **CowsQL/Raft** para armazenar o estado do cluster.

No gerenciamento de rede, o Incus pode trabalhar com diferentes tipos de rede. 
Por exemplo:
	`incus network create mynet`
	Por padrão cria uma rede do tipo `bridge` utilizando Linux Bridge.
Porém, se passarmos o tipo:
	`incus network create mynet --type=ovn`
	O Incus registra que existe uma rede chamada `mynet` e que ela é do tipo OVN. O Incus sabe que essa rede existe porque foi ele que recebeu e armazenou essa configuração. O OVN também passa a possuir uma representação dessa rede, mas em seus próprios termos: por exemplo, um Logical Switch.
	
### Incus + OVN

O Incus não fala com o OVN executando `ovn-nbctl`. Ele fala OVSDB protocol nativo, via biblioteca Go `libovsdb`, com modelos gerados a partir dos schemas:

```
internal/server/network/ovn/
├── ovn_nb.go           ← cliente NB      (schema/ovn-nb)
|
├── ovn_nb_actions.go   ← linhas de operações NB
|
├── ovn_sb.go           ← cliente SB      (schema/ovn-sb)
|
├── ovn_sb_actions.go / ovn_sb_events.go
|
├── ovn_icnb.go         ← cliente IC-NB   (schema/ovn-ic-nb)
|
├── ovn_icnb_actions.go ← transit switches
|
├── ovn_icsb.go         ← cliente IC-SB   (schema/ovn-ic-sb)
|
└── ovn_icsb_actions.go ← consulta de gateways

internal/server/network/ovs/
├── ovs.go / ovs_actions.go  ← cliente OVSDB do Open_vSwitch local (schema/ovs)

```

Na construção do cliente NB(`NewNB`), o Incus:
1. Monta o modelo do schema e adiciona índices de cliente por `name` para `Load_Balancer`, `Logical_Router`, `Logical_Switch`, `Logical_Switch_Port` (o `Get()` padrão do libovsdb só usa índices do schema). O Incus organiza dessa forma para que em suas buscas possa consultar apenas o nome do Logical Flow em seu respectivo tipo, sem precisar trabalhar com UUID.

2. Aceita múltiplos endpoints vindos do OVN separados por vírgula (suporte a cluster RAFT). Por exemplo, imagine que um cluster Raft do OVNNB-DB com três servidores:
	`OVN-NB-1 → 10.0.0.11:6641
	`OVN-NB-2 → 10.0.0.12:6641`
	`OVN-NB-3 → 10.0.0.13:6641`
	
	O Incus poderia receber algo como:
	`10.0.0.11:6641,10.0.0.12:6641,10.0.0.13:6641`
	
3.  Configura **TLS** se a string contiver `ssl:` (usando `network.ovn.client_cert` / `client_key` / `ca_cert`);
4. Conecta, faz `Echo()` e **`MonitorAll()`**, ou seja, mantém um **cache local completo do NB**, atualizado por push.
5. registra um inactivity check de 20s e um finalizador que cancela o monitor.

Por isso, o `incusd` é um cliente OVSDB assim como o `ovn-northd` ou o `ovn-controller`. Ele lê do cache local e escreve com transações OVSDB atômicas.

O Incus nunca fala com o SB para operar redes (o cliente SB existe para consultas pontuais e eventos). Quem consome o SB é o `ovn-controller` de cada nó (que o Incus não gerencia, ele é instalado e configurado fora de alcance do Incus).

Toda rede OVN do incus tem `id` numérico no banco de cluster, e todo nome derivado dele. É feita através da função `acl.OVNNetworkPrefix()`, que recebe um `networkID` e retorna `incus-net + networkID`. Por exemplo: `incus-net42-lr` é Logical Router associado à um `name` específico na rede com `id = 42`. Portanto, uma topologia resultante criada com Incus seria: 

```
       rede de uplink (bridge incusbr0 ou physical)
                    │  localnet
        ┌───────────┴────────────┐
        │   incus-net3-ls-ext    │
        └───────────┬────────────┘
                    │ lsp-router ⇄ lrp-ext (IP alocado de ipv4.ovn.ranges do uplink)
        ┌───────────┴────────────┐
        │   incus-net3-lr        │   SNAT de 10.x/24 → IP externo   (ipv4.nat=true)
        └───────────┬────────────┘   rotas default, policies, LBs
                    │ lrp-int (o gateway das instâncias)  ⇄  lsp-router
        ┌───────────┴────────────┐
        │   incus-net3-ls-int    │   DHCPv4/DHCPv6, RA, DNS, IPAM, ACLs
        └──┬────────────┬────────┘
           │            │
     instância c1   instância c2      (LSPs incus-net3-instance-<uuid>-eth0)
```

Repare que o Incus cria exatamente a topologia canônica de VPC do OVN: um switch interno privado, um roteador com NAT, e um switch externo que conecta a um `localnet`.

Agora, uma análise dos dois principais comandos de interação do Incus com o OVN:
1. `incus network create --type=ovn` 
	- Vamos utilizar uma versão mais real do comando:
		`incus network set incusbr0 ipv4.dhcp.ranges=10.0.0.10-10.0.0.100 ipv4.ovn.ranges=10.0.0.101-10.0.0.200` - Configura dois pools de IPs: O primeiro range para endereços que o DHCP do Incus pode atribuir. E o segundo endereços usados para as redes OVN

		`incus network create ovntest --type=ovn network=incusbr0 ipv4.address=10.10.10.1/24 ipv4.nat=true` - Cria uma nova rede lógica OVN, onde:
			- `incusbr0` é a rede física/uplink;
			- `ovntest` é uma rede lógica separada, com sua própria subnet `10.10.10.0/24`;
			- `10.10.10.1` é o endereço do router/gateway da rede OVN;
			- `ipv4.nat=true` permite que os endereços privados da `ovntest` sejam "NATeados" para a rede externa;
		
		Ou seja, `10.0.0.101 - 10.0.0.200` é um range reservado para uso do OVN no uplink, e `10.10.10.0/24` é a sub-rede criada para `ovntest`.
			  
	1. CLI → API: `incus`  monta `POST /1.0/networks` com o JSON da rede e envia pelo socket unix. Autenticação: uid/gid do peer no socket unix, ou certificado TLS.
	2. `incusd`- Validação e persistência: `Validate()` do driver `ovn` checa as chaves. `FillConfig()`/`populateAutoConfig()` preenche defaults (inclusive gerar sub-redes automaticamente se `ipv4.address=auto`). A rede é gravada no banco de cluster (dqlite) e recebe seu `id`, que determina todos os nomes OVN. Em cluster, a criação é um processo em duas fases (cada nó valida localmente, depois um nó executa a criação global).
	3. `setup()` - as transações OVSDB no Northbound: É reponsável por montar a rede OVN no OVNNB-DB, basicamente, cria no OVN toda a topologia lógica necessária. Na prática, essa função faz:
		1. Valida restrições de projeto e resolve qual rede de uplink usar.
		2. Calcula o MTU da bridge: se `bridge.mtu` não foi dado, deriva do underlay (`getOptimalBridgeMTU()`. Pega o MTU da interface do underlay e subtrai o overhead do encapsulamento).
		3. Deriva o MAC do roteador de forma estável: seed = `fingerprint do certificado do servidor + ID da rede`. Assim todos os nós do cluster geram o mesmo MAC, e dois Incus distintos na mesma rede física não colidem.
		4. `setupUplinkPort()`: aloca IPs externos do `ipv4.ovn.ranges`/`ipv6.ovn.ranges` da rede de uplink e prepara o lado do host (para uplink `bridge`: cria um par veth entre a bridge do Incus e uma bridge OVS, ou usa OVS nativamente; para `physical`: usa a interface/VLAN).
		5. `CreateChassisGroup`: o `HA_Chassis_Group` da rede.
		6. `CreateLogicalRouter` + `UpdateLogicalRouterMulticastRelay`.
		7. `CreateLogicalSwitch(ls-ext)`, `CreateLogicalRouterPort(lrp-ext)` (com o chassis group ⇒ distributed gateway port), `CreateLogicalSwitchPort(lsp-router)` + `UpdateLogicalSwitchPortLinkRouter` (o patch), e `lsp-provider` + `UpdateLogicalSwitchPortLinkProviderNetwork` (a porta `localnet`).
		8. `CreateLogicalRouterNAT("snat", ...)` para IPv4 e IPv6 se `ipv4.nat`/`ipv6.nat` estiverem ligados.
		9. `CreateStaticMACBinding` para o MAC do gateway do uplink, se a rede de uplink o declarar (evita depender de ARP para o próximo salto).
		10. Rotas default (`CreateLogicalRouterRoute`), incluindo, no modo `l3only`, uma rota de descarte para a sub-rede interna inteira (para que pacotes a IPs desconhecidos não escapem pelo uplink).
		11. `CreateLogicalSwitch(ls-int)` + `UpdateLogicalSwitchMulticastSnooping`.
		12. `bridge.external_interfaces`: cria LSPs e pluga interfaces físicas do host diretamente no switch interno (inclusive criando interfaces VLAN quando o formato estendido `nome/pai/vlan` é usado).
		13. `UpdateLogicalSwitchIPAllocation`: configura o IPAM do OVN (`other_config:subnet`, `exclude_ips`) no switch interno. É o OVN que aloca os IPs dinâmicos, não o Incus.
		14. `CreateAddressSet` / `UpdateAddressSetAdd` com as sub-redes internas: usado pelas ACLs.
		15. `logicalRouterPolicySetup()`: políticas de segurança do roteador (e exclusão de peers).
		16. `CreateLogicalRouterPort(lrp-int)`: o gateway das instâncias.
		17. `UpdateLogicalSwitchDHCPv4Options` / `DHCPv6Options`: cria os registros `DHCP_Options`: `server_id`, `server_mac`, `lease_time`, `router`, `dns_server`, `domain_name`, `mtu`, `classless_static_route`. O servidor DHCP é o próprio OVN, não um dnsmasq.
		18. `UpdateLogicalRouterPort(RA opts)`: Router Advertisement IPv6 nativo (`send_periodic`, `address_mode` slaac/dhcpv6_stateful, `mtu`, `rdnss`).
		19. `CreateLogicalSwitchPort(ls-int-lsp-router)` + link com o `lrp-int`.
		20. ACLs de baseline no switch interno, port group da rede, e os port groups das ACLs listadas em `security.acls`.
	4. A partir daqui, é apenas OVN:```
	incusd (libovsdb transact)
	   └─► OVN Northbound DB
	          └─► ovn-northd  → compila logical flows
	                 └─► OVN Southbound DB
	                        └─► ovn-controller (em cada nó)
	                               └─► OpenFlow → ovs-vswitchd
	                                      └─► genetlink → datapath do kernel
	                                      
2. `incus config device override c1 eth0 network=ovntest ipv4.address=10.10.10.42` e `incus start c1`
	- Conecta a interface de rede `eth0` da instância (VM) `c1` à rede OVN `ovntest` e define o IP `10.10.10.42` para `c1`. Após isso liga a instância, fazendo sua interface e configuração de rede entrarem em funcionamento.
	- Se quisermos adicionar outra VM nessa mesma rede, basta fazer:
		`incus config device override c2 eth0 network=ovntest ipv4.address=10.10.10.43` 
		
		`incus start c2`
