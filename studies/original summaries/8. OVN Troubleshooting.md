
Os agentes do OpenStack Neutron são classificados em 3 tipos:
- OVN Metadata agent - É o agente de `metadata` que executa nos Chassis do tipo Compute nodes
- OVN Controller agent - Agente do `ovn-controller` do tipo Chassi que executa nos Compute Nodes
- OVN Controller Gateway agent - Agente do `ovn-controller` do tipo Chassi Gateway que executa nos Gateway Nodes.

> Os agentes OVN Controller são obtidos pelo Neutron via OVNSB-DB. Se por algum problema, o serviço do `ovn-controller` não estiver registrado no OVNSB-DB ou não reportar um evento, o Neutron irá identificar o agente com status de DOWN.

A partir do OpenStack, podemos avaliar os status dos agents utilizando:
`$ openstack network agent list`

Uma forma de avaliar a conectividade entre OVN Central e o Chassi, seria verificar o valor do campo `nb_cfg` da table `Chassis_Private` (inclusive é o método que o Neutron utiliza para determinar o status dos agentes do OVN Controller).


O mau funcionamento desses serviços pode resultar em problemas como os descritos abaixo: 
- Em um cenário em que o serviço do ovn-controller estiver parado ou se o OVN Central tiver algum problema no cluster, ações como criar uma nova VM em um Compute Node pode resultar em um isolamento da VM. Isso ocorre devido ao OVS depender do serviço do ovn-controller para programar os Openflow flows 
- O serviço do ovn-controller pode ser reiniciado normalmente sem afetar o tráfego de rede das VMs do dataplane, porém ao reiniciar o serviço do OVS, haverá a perda de pacotes das VMs durante a instalação dos Openflow flows 
- O agente do OVN metadata executa funções muito importantes após a criação de uma VM. As principais configurações são como definir o hostname, configurar a chave pública de SSH e dentre outras personalizações do sistema operacional via cloud-init. Caso o mesmo venha sofrer uma reconexão com o OVN Southbound no momento da execução de alguma dessas funções, a VM poderá ter algum problema.

No nível de dataplane, antes do tráfego de rede ser tunelado com Geneve ou mesmo ser enviado localmente no mesmo Chassi, é possível monitorar o tráfego de rede via interface de rede tap de uma VM. Para que isso seja possível, verifique primeiramente em qual Compute Node que a VM está em execução:
	`$ openstack server list`
Conforme o output acima, utilize o instance name no seguinte comando:
	`$ virsh domiflist <instance-name>`
Por fim, utilizamos o nome da interface de rede vinda do output acima para verificar o tráfego de rede:
	`$ tcpdump -nni tap04a459b1-6e`
No output acima, podemos verificar que existe um tráfego de rede de ICMP ativo.

Durante qualquer troubleshooting, é preciso reunir a maior quantidade de informações possíveis para ajudar a determinar padrões que ajudarão a encontrar a causa raiz do problema:
- o problema ocorre em apenas uma VM ou em várias?
- é específico em um tenant do Openstack ou afeta vários?
- afeta o tráfego de rede local em um único Compute Node ou também é notado no tráfego de rede leste-oeste? Identifique os Compute Nodes afetados e verifique os componentes da solução
- avaliar a conectividade norte-sul, Gateway Nodes e também a conectividade de rede do Underlay
- existe load de CPU anormal no Compute Node/Gateway Node? Perda de pacotes no nível de Underlay?
- a VM tem conectividade com seu gateway de rede?
