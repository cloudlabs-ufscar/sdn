
- Um deployment de OVN consiste em alguns componentes:
	- Um Cloud Management System (CMS), que é uma aplicação externa (OpenStack, LXD/Incus, Kubernetes K8S)
	- Um database central que possui redundância lógica por funcionar em cluster
	- Um ou muitos hypervisors (compute nodes) que devem ter o OVS e que são identificados como **Chassis**
	- Nenhum ou vários **Chassi Gateway**, que são responsáveis em criar conectividade entre redes virtuais do Overlay com redes externas do Underlay (ex: Internet)

- A arquitetura do OVN se divide em duas camadas:
	- OVN Central (SDN Controller)
	- Chassi con ovn-controller: Hypervisors/Gateway Nodes que executam o OVS e que é gerenciado pelo OVN Central.

- Aprofundando mais nos componentes do OVN, temos:
	1. **CMS** - Traduz a configuração lógica de rede armazenada no banco de dados da CMS em um formato intermediário entendido pelo OVN
	2. **OVN Northbound Database** (OVNNB) - Recebe o formato intermediário das configurações lógicas de rede enviadas em um database. O schema do database deve usar conceitos utilizados do lado CMS, de modo que ele suporte diretamente noções de logical switch, routers, ACLs e assim por diante. Ele possui dois clientes: O CMS acima dele, e o ovn-northd.
	3. **ovn-northd** - Se conecta com o OVNNB-DB e com o OVNSB-DB. É responsável em traduzir a configuração lógica da rede a partir do OVNNB para logical datapath flows e inserir no OVNSB-SB.
	4. **OVN Southbound Database** (OVNSB) - É a parte central da solução, seus clientes são o ovn-northd e o ovn-controller, que está presente em todos os hypervisors (Chassis)/ Gateway Nodes. O OVNSB-DB possui 3 tipos de dados: 
		a. Physical Network Tables - Especificam como alcançar os hypervisors
		b. Logical Network Tables - Descreve a configuração lógica de rede em logical datapath flows
		c. Binding Tables - Faz uma ligação entre a Physical e a Logical Table
		- Os Gateway Nodes populam as PN tables e Port_Binding enquanto o ovn-northd popula as LN tables. Os componentes remanescentes são replicados em cada hypervisor. 
	5. **ovn-controller** - É um agente que executa em cada hypervisor. Para o norte, ele se conecta no OVNSB-DB para aprender sobre novas configurações e status, popular a PN table e a coluna Chassis na Binding table com status do hypervisor. Para o sul, se conecta com o ovs-vswitchd como um controller OpenFlow e com o ovsdb-server para permitir o monitoramento e controle da configuração do OVS.

- O fluxo de configuração de qualquer objeto no OVN é sempre **North-South**. O CMS irá enviar a configuração lógica de rede para o ovn-northd via OVNNB-SB. Por sua vez, o ovn-northd irá compilar essa configuração para um formato baixo nível e irá enviar para todos os hypervisors via OVNSB-DB.

- O OVN atualmente provê algumas formas de informação de status:
	- Para que o CMS detecte quando uma VM está em execução, o ovn-northd irá monitorar o valor da column `LOGICAL_PORT_CHASSI` (true ou false) da OVNSB-DB da tabela `PORT_BINDING` e atualizar a column `UP` na OVNNB-SB da tabela `LOGICAL_SWITCH_PORT`.
	- O OVN provê feedback para o CMS quando uma configuração solicitada entra em vigor. Nesse fluxo, existe uma sequência de passos:
		1. Quando o CMS solicita configurações para o OVNNB-SB, ao mesmo tempo é incrementado o valor da column `NB_CFG` na tabela `NB_GLOBAL`.
		2. Quando o ovn-northd compila as informações a partir do OVNNB-SB e insere no OVNSB-DB, o mesmo copia o valor da column `NB_CFG` do North para a tabela `SB_GLOBAL` do OVNSB-DB.
		3. Após o ovn-northd receber a confirmação que a configuração foi aplicada (vinda do ovn-controller), ele irá atualizar a column `SB_CFG` na tabela `NB_GLOBAL` OVNNB-DB para o valor de `NB_CFG` que foi incrementado anteriormente.
		4. O ovn-controller irá processar em cada hypervisor as modificações enviadas vindas do OVNSB-SB de acordo com o valor da column `NB_CFG` da tabela `SB_GLOBAL`, comparando com o valor de `NB_CFG` na tabela `CHASSI`. Após os physical flows serem instalados no OVS, o ovn-controller irá atualizar o valor de `NB_CFG` de seu respectivo hypervisor na tabela `CHASSI` do OVNSB-DB
		5. O ovn-northd monitora a column `NB_CFG` de todos os Chassis no OVNSB-DB e copia os valores atualizados para a column `HV_CFG` da tabela NB_GLOBAL do OVNNB-DB. Dessa forma o CMS pode saber que todas as configurações foram aplicadas em todos os hypervisors

- Um chassi pode ser classificado em:
	- **Chassi** (hypervisor) - É onde as VMS estarão em execução e todo o tráfego de redes **leste-oeste** é gerenciado por esse Chassi
	- **Chassi Gateway** - Responsável em criar conectividade norte-sul com ambientes externos (ex: Internet). Ele é configurado modificando o valor do `ovn-cms-options` para` enable-chassis-as-gw` localmente no OVS. 
	
	- Em cada Chassi será configurado o OVS com uma bridge dedicada para o OVN, chamada bridge integration (`br-int`). A `br-int` é criada automaticamente durante a inicialização do serviço do ovn-controller. As portas que serão conectadas na `br-int` são:
		1. Tunnel ports responsáveis em criar conectividade entre Chassis, sendo o ovn-controller responsável em adicionar, atualizar e remover tunnel ports.
		2. Em um Chassi Gateway, portas físicas utilizadas para criar conectividade norte-sul são adicionadas na `br-int`.


- O OVN Central é considerado como a Control Plane/SDN Controller e é composto pelos seguintes serviços: **OVNNB-DB**, **northd** e **OVNSB-DB**. As databases do OVN são gerenciadas pelo **ovsdb-server**, que possui alguns modelos de serviço para prover disponibilidade das databases:
	1. **Standalone** - Tudo sendo executado em um único servidor. Se o servidor tiver problema, as databases ficam indisponíveis.
	2. **Active-Backup** - Executa em 2 ou 3 servidores, onde um faz o papel de Active para responder as requisições dos componentes, e os demais servem como Backup, fazendo a replicação das databases a partir do Active. 
	3. **Clustered** - Executa em 3 ou 5 servidores em cluster, que sincronizam a escrita entre eles automaticamente. Utiliza-se o **Raft** para gerenciar o cluster que permitirá leitura e escrita conforme o status dos membros do cluster. Em um cluster, ocorrerá a eleição do **Leader** que permitirá leitura/escrita em suas databases, enquanto os **Followers** sincronizam as alterações a partir do Leader e apenas fazem leitura local. Em uma eleição são esperados os seguintes status:
		- Follower - Esse é o primeiro estado após o servidor entrar no cluster.
		- Candidate - Quando não existe um Leader no cluster, inicia-se a eleição e o estado muda para Candidate.
		- Leader - Se receber a maioria dos votos, o estado passa para Leader e o restante mudam seus status para Follower.
		
> O Leader é definido para o OVNNB e para o OVNSB.

- Em um cluster de OVN Central, caso se queira executar um comando em um node que não seja o leader, utilize o parâmetro --no-leaderonly conforme abaixo:
	`$ ovn-sbctl --no-leader-only list Chassis`

- Para que os componentes do OVN Central possam processar as requisições dos clientes e evitar gargalos, existem timers que são configurados entre os componentes:
	- OVN Central - `inactivity_probe` (NB/SB) = 180 secs
	- OVN-Controller - `ovn-remote-probe-interval` = 180 secs e `ovn-openflow-probe-interval` = 0 secs

- As portas TCP de serviço utilizadas pelos daemons do OVN Central são:
	- 6641 - OVNNB-DB
	- 6642 - OVNSB-DB
	- 6643 - Utilizado pelo Raft para o Northbound
	- 6644 - Utilizado pelo Raft para o Southbound


- Os **Logical Flows** são semelhantes com o OpenFlow, pois são compostos por flow tables com priority, match e actions. Uma grande diferença é que os Logical Flows descrevem o comportamento detalhado de uma topologia de rede que pode abranger um grande número de hosts. Portanto, o OVN centralmente programa as topologias de rede em Logical Flows, que são distribuídos através do OVN-Controller que executam em cada host. Com isso o OVN-Controller sabe como traduzir Logical Flows em OpenFlow utilizando o estado atual da rede física. Os Logical Flows podem ser definidos como:
	- **Logical Switch (LS)** - Semelhante a um switch ou para uma subnet L2.
	- **Logical Router (LR)** - Similar a um router (o mesmo é distribuído).
	- **Logical Switch Port (LSP)** - Pontos de conectividade ingress/egress e geralmente são conectadas com VMs.
	- **Logical Router Port (LRP)** - Pontos de conectividade ingress/egress entre um LS e um LR.

- O funcionamento dos Logical Flows é dado da seguinte forma:
	- O OVN irá definir o LS usando dois pipelines: **ingress pipeline** e **egress pipeline**.
	- Quando um pacote entra no LS, o ingress pipeline será executado onde o pacote foi originado. Se o destino é o mesmo do host, então o egress pipeline é executado. Se o destino é remoto, o pacote é enviado via tunnel antes de executar o egress.

- Comandos úteis:
	1. `ovn-sbctl lflow-list` - Verifica os pipelines criados automaticamente
	2. `ovn-trace DATAPATH MICROFLOW` - Onde temos que:
		- Datapath = Identifica o Logical Datapath (LR ou LS) onde o sample packet irá iniciar
		- Microflow = Descreve o sample packet que irá ser simulado
		- O `ovn-trace` suporta vários níveis de detalhamento:
			2.1. Minimal: Apenas o output do sample packet
			2.2. Sumary: Fluxo ingress/egress, valor das variáveis e actions
			2.3. Detailed: Número das flow tables, flow match, nome dos estágios do pipeline que o sample packet será processado, priority e mais.


- Os arquivos de log estão localizados em:
	- OVN Central:
		- OVN Northbound database - /var/log/ovn/ovsdb-server-nb.log
		- ovn-northd - /var/log/ovn/ovn-northd.log
		- OVN Southbound database - /var/log/ovn/ovsdb-server-sb.log
	- Chassi:
	- ovn-controller - /var/log/ovn/ovn-controller.log 
	- ovsdb-server - /var/log/openvswitch/ovsdb-server.log 
	- ovs-vswitchd - /var/log/openvswitch/ovs-vswitchd.log
