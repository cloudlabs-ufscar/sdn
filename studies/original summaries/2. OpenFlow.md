
- O OpenFlow foi criado para ser o Open Programmable Network Protocol para configuração e gerenciamento de equipamentos de rede de diferentes fabricantes, portanto é universal. A ideia fundamental do OpenFlow é olhar os campos de um pacote, verificar se eles combinam com alguma regra, se positivo, executar uma ação.

- Arquitetura do OpenFlow:
	1. **OpenFlow Switch**: São switches que utilizam o protocolo OpenFlow.  Quando um pacote entra em um switch Openflow, ele irá buscar por um flow matching em suas flow tables e executar a action correspondente. Se não existir correlação (flow missing), o switch irá perguntar ao Controller e este irá responder com o novo flow que deverá ser instalado para manipular o fluxo desse pacote.
	2. **OpenFlow Controller**: Cria regras de data-forwarding de cada switch OpenFlow através do OpenFlow Protocol.
	3. **OpenFlow Protocol**: Usado para criar a comunicação entre Controller e switch.

- Relação do OpenFlow com o OVS: O OVS é um tipo de switch OpenFlow, utilizado em conjunto com soluções de virtualização para criar conectividade entre workloads. É possível distinguir onde entre as funcionalidades do OVS comparadas às do OpenFlow pensando da seguinte forma:
	"*Pensando no OVS como um switch, existem duas coisas configuráveis: A estrutura do switch (existe uma bridge `br0`? quais portas pertencem à ela? qual o tipo da interface?), que é controlado pelo OVS, através de configurações presentes no OVSDB. E o comportamento do switch (Se chegar um pacote com MAC `dst X`, pra qual porta vai?), que é controlado pelos OpenFlow flows.*"

>O que junta ambos os conceitos de configuração + comportamento é o `ovs-vswitchd`, já que ele atua em ambos: Recebe a configuração estrutural através do OVSDB, trabalha com flows OpenFlow e controla o datapath que efetivamente encaminha os pacotes.

	Dessa forma, podemos ter alguns tipos de flow matching:
	1. **L1 Matching**: Direciona todo o tráfego sem fazer nenhuma checagem
	2. **L2 Matching**: Vê o MAC address do pacote e compara com o MAC dst definido no flow.
	3. **L3 Matching**: Vê o IP address do pacote e compara com o IP dst definido no flow.
	4. **L4 Matching**: Vê o TCP do pacote e compara com o TCP dst definido no flow.
	5. **Flow-based forwarding**: Combina os tipos acima para filtrar pacotes que tenham múltiplas características.
	
- Quando estamos tratando de matching, quase sempre será necessário utilizar o parâmetro `arp, action = normal`, que na prática significa: 
	`MATCH: EtherType = ARP´
	`ACTION: NORMAL`
	
	Ou seja, o `NORMAL` manda o OVS tratar ARP como um switch Ethernet convencional. Isso é necessário porque, a nível físico, é preciso saber qual o destino do pacote.
	
- Uma **action** é o que vai acontecer se ocorrer o match. Por exemplo, se der match no flow, direcione o pacote para a porta 2, se não, para porta 3.

- É possível definir prioridade entre flows, manipulando o valor **priority**, onde quanto maior for seu valor, maior será sua prioridade de dar match antes dos flows com prioridade menor. 

- Quando vamos definir um flow, existem algumas siglas importantes:
	1. `dl_`: Data Link (Ethernet)/ L2 (por exemplo, `dl_src` e `dl_dst`)
	2. `nw_`: Network (IP)/L3 (por exmeplo, `nw_src` e `nw_dst`) 
	3. `tp_`: Transport (TCP/UDP)/L4 (por exemplo, `tp_src` e `tp_dst`)

- O **pipeline** é todo o trajeto que o pacote percorre desde sua entrada na NIC até sua saída. Combinando múltiplas flow tables, é possível gerar diferentes pipelines, a depender da entrada, servindo para múltiplos propósitos, como realizar o lookup do pacote, executar alterações no header do pacote ou como executar o NAT. Utilizando flow tables encadeadas em um pipeline se torna possível até mesmo direcionar diferentes pacotes para destinos diferentes, como por exemplo, uma flow table direciona o pacote para uma VM, e outra flow table direciona para outro hypervisor. 
> Um exemplo é utilizar 3 flow tables, uma para controle de acesso, outra para NAT e a ultima para a propagação dos pacotes em si. Nesse cenário, por exemplo, 2 hypervisors em sub-redes diferentes passariam pelo fluxo de NAT e conseguiriam se comunicar, já hypervisors na mesma sub-rede só pularia a parte do NAT e transmitiriam seus pacotes via ARP e IP apenas.
