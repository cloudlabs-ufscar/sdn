## 2. Leste-Oeste

A conectividade leste-oeste se resume na comunicação de rede entre workloads que estão na mesma localidade. Existe alguns tipos:
	- Entre workloads que estão na mesma subnet: No mesmo compute node ou em diferentes compute nodes. Por exemplo:
		`Subnet 10.0.0.0/24 `
		 `VM1: 10.0.0.10` 
		 `VM2: 10.0.0.20`
		Elas estão na mesma L2/Subnet (mesmo LS). Se estiverem em Chassis diferentes, o Geneve simplesmente transporta a L2 pelo underlay, não precisa de roteamento IP entre as VMs pois eslas estão na mesma subnet. 

Entre worloads que estão em diferentes subnets porém abaixo do mesmo router: No mesmo compute node ou em diferentes compute nodes. Por exemplo:
		`Subnet 10.0.0.0/24 `
		 `VM1: 10.0.0.10` 
		`Subnet 20.0.0.0/24 `
		 `VM2: 20.0.0.10` 
		Agora não existe conectividade L2 direta entre VM1 e VM2, para uma se comunicar com outra o pacote precisa passar pelo Logical Router e fazer o L3 Routing. Se tiverem em Chassis diferentes, o Geneve também pode ser usado para transportar esse tráfego entre os Chassis. 
		
O **Logical Switch possui um pipeline de Ingress e outro de Egress** e a direção é da perspectiva do Logical Switch. O último objetivo do pipeline de Ingress é determinar a porta de output e enviar o pacote para o pipeline de Egress. Sendo que o pipeline de Egress irá realizar algumas validações de segurança e irá entregar o pacote para seu destino. Dois pontos são importantes para entender sobre os pipelines: 
	- Ambos podem estar localizados no mesmo ou em diferentes Chassis sendo que no caso de estarem em diferentes Chassis, o pacote será enviado por um túnel Geneve.
	- O pipeline de Egress não possui o estágio de Destination Lookup, ou seja, o que exige que a porta de output precise ser determinada no pipeline de Ingress. Isso significa que o Destination Lookup não precisa ser executado duas vezes.
	  
Podemos verificar o resumo dos estágios de cada pipeline no diagrama abaixo:                              
	![[LS Datapath.png]]
	
1. **Port Security (Ingress)** - Verifica se os pacotes que estão ingressando na Switch Logical Port possuem os endereços de MAC Address e IP de origem corretos.
2. **Egress ACL** - Da perspectiva de uma VM, o tráfego de rede será de Egress e de acordo com o que o Neutron programou no Security Group, todo o tráfego de rede de Egress da VM estará liberado. 
3. **ARP Responder** - Para a requisição de resolução ARP, será gerado a resposta fazendo a troca entre MAC Address de origem com o de destino.
4. **DHCP Processing** - O funcionamento do DHCP ocorre através da manipulação dos flows.
5. **Destination Lookup** - Verifica qual é o MAC Address de destino e determina a porta de output.
6. **Ingress ACL** - Implementa as rules de Ingress do Security Group do Neutron. Neste exemplo, existe uma rule que libera conexões de Ingress do SSH. O princípio, o funcionamento é o mesmo, pacotes que tem match em uma table são submetidos para outra table de connection tracking.
7. **Port Security (Egress)** - Verifica se os pacotes que estão ingressando na Switch Logical Port possuem os endereços de MAC Address e IP de destino corretos:

O **Logical Router também possui seus pipelines de Ingress e Egress**:                                        
	![[LR Datapath west-east.png]]

1. **Port Security** - Faz uma checagem de segurança para os pacotes que estão ingressando na Logical Router Port.
2. **IP Input** - Executa algumas checagens no nível de L3 e implementa no Logical Router algumas manipulações com flows para o mesmo responder a ICMP e ARP Reply.
3. **IP Routing** - Implementa o roteamento baseado no endereço IP de destino. Nesse estágio, é decidido a porta de output, TTL do pacote é decrementado e o next hop é definido.
4. **Next Hop Resolver** - Realiza o discover do MAC Address do IP de destino para entregar o pacote. Nesse caso, para o tráfego de rede leste-oeste, os MAC Addresses já são conhecidos pelo OVN Southbound e portanto existirão flows definidos.
5. **Output** - Envia o pacote para a porta de output definida durante o estágio do IP Routing.

## 3. Norte-Sul

A conectividade norte-sul se resume na **comunicação de rede entre workloads internos com ambientes externos** e vice e versa. Os Logical Routers são distribuídos entre os Chassis e são responsáveis pelo roteamento e NAT de acordo com o tipo do Chassi.

Os Logical Routers possuem regras de NAT para implementar o DNAT (1:1) e SNAT (1: para muitos). Do ponto de vista do OVN Northbound, podemos visualizar as portas criadas de um Logical Router e também as regras de DNAT e SNAT:
`$ ovn-nbctl show <router-id>`
O campo `external ip` que é o endereço IP utilizado para o DNAT ou SNAT.

Analisando agora o pipeline do Logical Router, mas agora no tráfego norte-sul:                     
	![[LR Datapath north-south.png]]

1. **Port Security** - Faz uma checagem de segurança para os pacotes que estão ingressando na Logical Router Port.
2. **IP Input** - Executa algumas checagens no nível de L3 e implementa no Logical Router várias manipulações com flows para o mesmo responder a ICMP e ARP Reply.
3. **UNSNAT** - Faz a tradução do endereço de IP de destino para o endereço real interno para o tráfego de rede vindo de uma rede externa.
4. **DNAT** - Implementa o NAT 1:1 do IP externo para um IP interno.
5. **IP Routing** - Implementa o roteamento baseado no endereço IP de destino. Nesse estágio, é decidido a porta de output, TTL do pacote é decrementado e o next hop é definido.
6. **Next Hop Resolver** - Realiza o discover do MAC Address do IP de destino para entregar o pacote. Nesse caso, para o tráfego de rede norte-sul, os MAC Addresses externos aprendidos serão armazenados na table MAC_Binding do Southbound database.
7. **SNAT** - Implementa o SNAT, traduzindo o IP de origem e portas TCP/UDP de uma subnet para um endereço IP externo.
8. **Output** - Envia o pacote para a porta de output definida durante o estágio do IP Routing.
