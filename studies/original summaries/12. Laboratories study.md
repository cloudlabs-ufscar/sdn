## Os componentes do ovn-ic

| Componente                 | Papel                                                                                                                                                                                   |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **IC-NB** `6645`           | Banco global com a intenção da federação: quais transit switches existem, quais AZs participam. Tabelas: `Transit_Switch`, `Availability_Zone`.                                         |
| **IC-SB** `6646`           | Banco global com o estado de runtime: `Gateway` (chassis registrados por AZ), `Route` (rotas anunciadas/aprendidas), `Port_Binding`, `Encap`.                                           |
| **`ovn-ic`**  <br>1 por AZ | A ponte. Conecta quatro bancos ao mesmo tempo (IC-NB + IC-SB globais, NB + SB locais). Propaga o transit switch, registra o gateway da AZ, anuncia rotas locais e injeta as aprendidas. |
| **Transit switch**         | Logical switch declarado só no IC-NB. O `ovn-ic` o materializa em cada NB local com a anotação `interconn-ts`. É o backbone L2 entre os routers das AZs.                                |
| **Gateway chassis**        | Chassis que termina os túneis GENEVE vindos das outras AZs. Precisa de `ovn-is-interconn=true` no OVS e de `lrp-set-gateway-chassis` na LRP de trânsito.                                |
##  O fluxo de federação

1. `ovn-ic` lê `NB_Global.name` → descobre que esta AZ se chama az1
2. registra `Availability_Zone` “az1” no IC-SB
3. vê chassis com `ovn-is-interconn=true` → cria a linha `Gateway` no IC-SB
4. lê `Transit_Switch` “ts” no IC-NB → **cria o LS “ts” no NB local**
5. operador conecta `lr-az1` ao “ts” (`lsp-ts-az1` ↔ `lrp-az1-ts`)
6. vê `lrp-az1-ts` com gateway chassis → publica o `Port_Binding` no IC-SB
7. `ic-route-adv`: publica `10.10.1.0/24` no IC-SB como rota de az1
8. `ic-route-learn` da az2 lê essa rota → injeta em `lr-az2` como `(learned)`
9. `ovn-controller` da az2 vê o Port_Binding remoto → **sobe o túnel GENEVE** para o encap-ip de az1
## O caminho de um pacote inter-AZ

`app-vm-1` (10.10.1.10 - AZ1) → `db-vm` (10.10.2.10 - AZ2)

1. container escreve o pacote em `eth0` (MTU 1442)
2. veth → `br-int` (AZ1); `ovn-controller` aplica o pipeline de `ls-az1`
3. destino não é local → sai pelo `lsp-az1-router` para `lr-az1`
4. `lr-az1` consulta rotas: `10.10.2.0/24 via 169.254.100.2 (learned)`
5. pacote entra no datapath do transit switch `ts`
6. o `Port_Binding` de `lsp-ts-az2` aponta para `az2-chassis`
7. `br-int` encapsula em **GENEVE** (UDP 6081): `172.18.3.175 → 172.18.33.126`
8. underlay entrega; `br-int` da AZ2 desencapsula
9. `lr-az2` roteia para `ls-az2` → `Port_Binding` local de `lsp-db-vm`
10. veth → `eth0` do `db-vm`

## Cálculo MTU

**Overhead GENEVE = 58 bytes**: IP externo (20) + UDP (8) + cabeçalho GENEVE (8) + opções (8) + Ethernet interna (14). Daí `1500 − 58 = 1442` de MTU no workload. E o maior payload de ping sem fragmentar é `1442 − 28 = 1414` (IP 20 + ICMP 8).

## 2. `advanced-ovn-ic`

### As três propriedades estruturais

1. **Dois planes isolados**: Um client (tenant) e um mgmt, cada um federado pelo seu próprio transit switch, sobre um único GENEVE. O banco vive só no mgmt e é inalcançável do tenant.
2. **Um edge por célula**: Os dois plane routers entregam o nort-sul a um router de gateway por AZ, que faz SNAT de cada plano para um endereço externo próprio.
3. **Interconexão em HA**:  IC-NB/IC-SB como cluster RAFT de 3 membros, então nenhuma VM sozinha derruba os bancos compartilhados da federação.

Dessa forma, assim está dispostas as 3 VMs que simularam AZs (e quórum):

| VM                         | Papel           | O que roda                                                                                                       |
| -------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------- |
| az1  <br>`172.18.3.175`    | célula completa | Incus, NB/SB/northd/`ovn-controller`, `ovn-ic`, chassis, edge, **membro RAFT + bootstrap**                       |
| az2  <br>`172.18.33.126`   | célula completa | idem, **membro RAFT**                                                                                            |
| quorum  <br>`172.18.3.240` | **árbitro**     | **só** o terceiro membro do cluster RAFT. Sem chassis, sem `br-int`, sem GENEVE, sem workloads, sem NB/SB local. |
>[`azs`] = az1, az2 - As AZs reais, com chassis, workload, GENEVE
>[`ic_cluster`] = az1, az2, quorum - os três nós do cluster RAFT. É por isso que o árbitro nunca recebe nenhuma task de chassis ou de topologia.

| Load balancer | VIP por AZ + service VIP na AZ1         | não possui                                          |
| Membros       | `app-vm-1`, `app-vm2,` `load-vm`        | `app-vm-1`, `app-vm2`, `db-vm`, `load-vm`, `obs-vm` |

> Os dois `ts` são carregados pelo mesmo túnel GENEVE entre os mesmos dois chassis. O que os separa é serem datapaths OVN distintos. Uma possível melhoria seria implementar essa separação.

O netplan mantém a separação entre os planes por NIC. É importante para que cada plano possua sua própria interface e suas próprias rotas, reduzindo a possibilidade de mistura acidental de tráfego. Além do default route (na NIC marcada `default-route: true`), cada NIC recebe uma rota explícita para o supernet do seu próprio plane:

```
    eth0:                          # client
      addresses: [10.10.1.10/24]
      mtu: 1442
      routes:
        - {to: default, via: 10.10.1.1}
        - {to: 10.10.0.0/16, via: 10.10.1.1}    # client fica preso aqui
    eth1:                          # mgmt
      addresses: [10.20.1.10/24]
      mtu: 1442
      routes:
        - {to: 10.20.0.0/16, via: 10.20.1.1}  # o banco SÓ sai por esta NIC
        - {to: 172.18.0.0/16, via: 10.20.1.1}   # underlay: consultar o probe agent
```
Assim o tráfego para `10.20.0.0/16` fica preso à NIC de gerência e nunca sai pela de client. E o `db-vm` tem **uma única** NIC, não existe endereço que o client plane pudesse sequer usar para nomeá-lo.
> **Importante**: `x.x.1.1` indica o IP do gateway.

### Gateway Nodes

Representado pelo esquema abaixo:                                                                                                            
	![[gateway node.png|664]]

O `edge: 192.168.251.x` é uma rede de trânsito entre os routers internos e o edge router.
A sub-rede `192.168.241.x` é a rede externa/uplink. Ele possui `.241.2` e `241.3` porque ele tem uma interface/porta externa por plane.
Então o router edge faz SNAT: 
`Client plane (10.10.1.10) -> lr-client-az1 (192.168.251.1) -> lr-edge -> lr-edge-az1 -> SNAT -> 192.168.241.2 -> br-ex (192.168.241.1) Internet`
> A única alteração no IP de origem é o SNAT `10.10.1.10 -> 192.168.241.3`, o resto são apenas hops. O `192.168.241.3` não vira `192.168.241.1`. O `.3` é o IP de origem usado pelo edge após o SNAT, enquanto o `.1` é o gateway/next-hop que recebe esse pacote para encaminhá-lo ao uplink.

Conceitos importantes sobre o Gateway Node:
1. A porta do plane router para o edge é plana: Ou seja, funciona apenas como conexão lógica entre dois routers, não recebeu `lrp-set-gateway-chassis`. Dessa forma, não é uma DGP (Distributed Gateway Port). Isso é importante porque o OVN tem uma restrição para LB: um router que hospeda o LB não pode ter mais de uma DGP.
>  `lrp-set-gateway-chassis` seria associar uma determinada LRP a um ou mais chassis que poderão atuar como gateway para aquela porta. Quando uma LRP recebe um `Gateway_Chassis`, ela passa a ser uma DGP.
>  DPG = É uma Logical Router Port (LRP) especial que conecta um Logical Router à parte externa da rede e tem um Gateway Chassis responsável por executar o tráfego externo.

2. As rotas de volta no edge são no supernet do plane: O `lr-edge` conhece 10.10.0.0/16, ao invés de conhecer apenas um dos dois planes (client de cada AZ). Isso importa muito pro LB, que precisa conhecer os dois lados (AZ1 e AZ2).

3. Foram criadas duas policies para impedir o tráfego entre planes: `10.10.0.0/16 ⇄ 10.20.0.0/16`.

4. O acesso externo se dá pela `br-ex`, saindo no underlay pela NIC `ens3`. Faz MASQUERADE (Tipo de NAT, mas que troca a origem pelo IP da interface de saída) para acesso à internet. Ou seja, há dois NATs, e ele pode transformar `src = 192.168.241.2` no IP que o host possui na `ens3`.

```
ic_nb_remote: "{{ groups['ic_cluster'] | map('extract', hostvars, 'az_private_ip')
```

Passo a passo mais detalhado:
**IDA:**
- **Etapa 1:** O SSH é necessário para conectar na az1 para enviar a requisição para o endereço certo. Ou seja, o comando:
  `ssh -L 8080:10.10.1.100:80 az1` abre a porta 8080 na máquina local, e tudo que chegar nela, ele manda pela conexão SSH para o `sshd` na AZ1. Quando chega os bytes o `sshd` abre uma nova conexão:
- **Etapa 2:** O kernel da az1 consulta a rota:
  `10.10.1.100/32 (dst) via 192.168.241.2 (src) dev br-ex`, a interface de saída é `br-ex`, então o kernel escolhe o IP dela como origem:
	`src 192.168.241.1` `dst 10.10.1.100:80`
- **Etapa 3:** O pacote chega a `br-ex` AZ1 `192.168.241.1`, o hop é `192.168.241.2` (client, se fosse mgmt seria `192.168.241.3`), que é a porta externa do `lr-edge-az1`. Em L2, o host faz ARP pra descobrir o MAC dessa porta, que retorna o MAC da porta externa do edge. Porém em L3 o destino ainda é o VIP, então `br-ex -> ls-ex-az1 -> lr-edge-az1` (até aqui, só foi feito encaminhamento).
- **Etapa 4:** O `lb-web-az1` está associado ao` lr-edge-az1`, ele recebe src/dst e faz duas coisas:
	  - DNAT: O VIP `10.10.1.100:80` é traduzido para `10.10.1.10:80`
	  - Force-SNAT: `192.168.241.1 -> 192.168.251.254` (traduz o endereço de `br-ex` para a porta interna do `lr-edge`, o que obriga a resposta usar ele para o caminho de volta).
- **Etapa 5:** Agora o destino é `10.10.1.10`, o `lr-edge-az1` tem rota para o supernet client: `10.10.0.0/16 via 192.168.251.1` (`ls-edge-az1`), que direciona para o próximo hop: `lr-client-az1`.
- **Etapa 6:** `lr-client-az1` envia para `ls-client-az1` e o OVN encontra o `Port_Binding` de `lsp-app-vm-1-client`, que já está local naquele chassis.
- **Etapa 7:** Finalmente `veth -> eth0 da app-vm-1`, o nginx recebe: 
	`src = 192.168.251.251` `dst = 10.10.1.10:80`
- **Etapa 8:** O nginx abre uma conexão TCP para `10.10.1.200:80`, servindo como um reverse proxy, porque o `location /api/` usa:
	`proxy_pass hhtp://10.10.1.200:80`
	Então agora temos uma nova conexão:
	`src = 10.10.1.10:52000` `dst = 10.10.1.200:80`
- **Etapa 9:** O nginx faz ARP por `10.10.1.200` por L2 (já que estão na mesma sub-rede), e o LB responde ao ARP, fazendo o VIP parecer presente na rede.
- **Etapa 10:** O LB (Service VIP) associado ao client plane recebe 
	`src = 10.10.1.10:52000` `dst = 10.10.1.200:80` 
	E faz DNAT:  `10.10.1.200 -> 10.10.2.20:8080`
	Agora temos uma tradução de destino em outra AZ.
- **Etapa 11:** Agora o pacote é: 
	`src = 10.10.1.10` `dst = 10.10.1.200:80` 
	O `lr-client-az1` sabe, via OVN-IC que o dst está na AZ2, `via 169.254.100.2`, é uma rota `learned`. Então:
	`10.10.1.10 -> 169.254.100.2 -> ts-client -> AZ2` 
	Ocorre o 2° Force-SNAT:
		`src=10.10.1.10 -> dst = 10.10.2.20:8080
	Porque quando o backend responder, ele deve responder para `169.254.100.1` que é o outro lado do transit switch, assim a resposta é obrigada a retornar pelo `ts-client`.
- **Etapa 12:** O pacote entra no `ts-client` e o `Port_Binding` da porta remota aponta para `az2-chassis`. O pacote lógico ainda é:
	`src = 169.254.100.1` `dst = 10.10.2.20:8080` 
	Mas para atravessar o underlay ele é encapsulado via GENEVE:
	`src = 172.18.3.175 dst = 172.18.33.126 UDP dst = 6081`
- **Etapa 13:** O `br-int` da AZ2 recebe, desencapsula e recupera o endereço lógico. Depois:
	`ts-client -> lr-client-az2 -> ls-client-az2 -> Port_Binding local -> app-vm-2`
- **Etapa 14:** O JDBC faz `10.20.2.20 → 10.20.2.10:5432` para acessar `db-vm`. E a rota `10.20.2.10/24` está conectada em `eth1` para isolamento. Então:
	`10.20.2.20 -> eth1 -> ls-mgmt-az2 -> db-vm (10.20.2.10)`
	É simplesmente L2 dentro de uma mesma sub-rede. 
	
**VOLTA:**
- **Etapa 15:** O PostgreSQL responde: 
	`src = 10.20.2.10:5432 dst = 10.20.2.20:38000`
	Fazendo o caminho contrário da etapa anterior.
- **Etapa 16:** Agora o Java precisa responder para quem originou a conexão. Ele viu o request vindo de `169.254.100.1` então responde para ele. Percorrendo o caminho: `app-vm-2 10.10.2.20 -> lr-client-az2 10.10.2.1 -> ts-client`.
- **Etapa 17:** O GENEVE encapsula mais uma vez o pacote e endereça via underlay, a `br-int` da AZ1 desencapsula.
- **Etapa 18:** o `lr-client` desfaz o SNAT que tinha feito para saber o destino do pacote na AZ. 
	Antes: `10.10.1.10 -> SNAT -> 169.254.100.1`
	Agora: `169.254.100.1  -> SNAT -> 10.10.1.10`
	Então o pacote volta a ser destinado ao nginx:
	`src = 10.10.2.20:8080 dst = 10.10.1.10:52000`
- **Etapa 19:** Agora é o LB que desfaz o DNAT do Service VIP:
	Antes: `10.10.1.200:80 -> DNAT ->10.10.2.20:8080`
	Agora: `10.10.2.20:8080 -> reverse DNAT -> 10.10.1.200:80`
	O nginx recebe `src = 10.10.2.20:8080 dst = 10.10.1.10:52000`
- **Etapa 20:** Agora o nginx devolve a resposta HTTP para a conexão original. Ele precisa responder para:
	`src 10.10.1.10:80   dst 192.168.251.254:41000`
	O caminho é: `app-vm-1 10.10.1.10 -> lr-client-az1 -> ls-edge-az1 -> lr-edge-az1`.
- **Etapa 21:** No `lr-edge` é feito o reverse force-SNAT.
	Antes: `192.168.241.1 -> 192.168.251.254`
	Agora: `dst: 192.168.251.254 -> reverse SNAT -> 192.168.241.1`
	E é feito também o reverse do DNAT do primeiro VIP.
	Antes: `10.10.1.100 -> 10.10.1.10`
	Agora: `dst:10.10.1.10 -> reverse DNAT -> 10.10.1.100`.
	Então o host AZ1 recebe: `src = 10.10.1.100:80 dst 192.168.241.1:41000`
- **Etapa 22:** A resposta finalmente chega ao browser:
	`lr-edge-az1 -> ls-ext-az1 -> br-ex -> host AZ1 -> sshd -> SSH tunnel -> SSH client -> browser`
	O browser recebe o `HTTP response` como se tivesse simplesmente feito `localhost:8080 -> localhost`

> **IMPORTANTE:** Nenhuma tradução de volta é configurada. O OVN mantém o `conntrack` (estado de conexão), e cada NAT é desfeito automaticamente no mesmo ponto onde foi feito. Ou seja, para que a volta acontecesse, não foi preciso implementar nada, o OVN cuida disso.

**O Backend em java**: 
	- Toda a configuração vem do ambiente (`APP_AZ`, `APP_CLIENT_IP`, `APP_MGMT_IP`, `DB_HOST`, `APP_PROBE_AGENTS`…), então o código não carrega endereço nenhum.

| Endpoint      | O que faz                                                                     |
| ------------- | ----------------------------------------------------------------------------- |
| `/api/health` | liveness + identidade da camada                                               |
| `/api/status` | identidade, endereços dos dois planes, NICs com MTU, latência do banco        |
| `/api/infra`  | lê `infra_state` do banco — o que o dashboard renderiza                       |
| `/api/flow`   | o caminho do request com tempo medido por salto                               |
| `/api/test`   | roda ao vivo as checagens dos botões “Testar”; ?group= filtra                 |
| `/api/orders` | escreve uma linha em orders.                                                  |
| `/api/report` | agregação sobre a tabela orders inteira, leitura deliberadamente mais pesada. |
Dois listeners, dois planes, um processo:
```
HttpServer server  = HttpServer.create(new InetSocketAddress(PORT), 0);                   // client plane
HttpServer metrics = HttpServer.create(new InetSocketAddress(MGMT_IP, METRICS_PORT), 0);  // mgmt plane
```

O serviço é oferecido ao tenant no client plane; a instrumentação dele (`/metrics`, porta 9102) é assunto de operação e vive no mgmt, **bindada explicitamente ao IP de gerência**. Raspar o backend a partir da rede de tenant é impossível por construção, não por política.

### Load Balancer

Um mesmo VIP é anexado em três lugares:                                                                                                                                              
	![[VIPs LB.png]]

1. VIP no `ls-client`: O workload precisa enxergar o LB, por isso, ele é anexado ao Logical Switch. Assim, o OVN consegue fazer o VIP responder o ARP do workload e enviar o pacote.
2. VIP no `lr-edge`: O tráfego vindo de fora precisa ser intermediado para o workload, por isso, ele é anexado ao Logical Router de borda. Assim, o LB pode fazer o DNAT e enviar o pacote.
3. VIP no `lr-client-az1`: O mesmo serviço deve ser acessado por uma workload de outra AZ. Assim, o LB associado ao plane router permite que uma origem remota que chega pelo caminho do interconnect também seja atendido pelo VIP.

### Observabilidade e geração de carga

Cada célula roda o **próprio** Prometheus + Grafana, no **plane de gerência**.

```
obs-vm (só mgmt)   raspa, tudo pelo management plane
  ├── node_exporter do host de AZ  :9100 ← contadores por interface, incl. genev_sys_6081
  |
  ├── agente de probe da infra :9101   ← estado do OVN como métrica
  |
  ├── cada workload :9100 ← bytes por NIC: client vs mgmt, lado a lado
  |
  ├── backend Java :9102 ← RPS, histograma de latência, latência de DB
  |
  ├── postgres_exporter   :9187  ← commits, rows, conexões
  |
  └── gerador de carga :9103 ← carga oferecida e latência do cliente
```

- `genev_sys_6081` nos contadores do host é o detalhe mais elegante: bytes/s no túnel vira métrica real, não inferência.
- Cada célula raspa só a si mesma: uma falha numa AZ não cega o monitoramento da outra, e o scrape nunca carrega a interconexão. O efeito colateral: painéis de um componente que só existe numa AZ ficam vazios no Grafana da outra. Isso é o isolamento funcionando.
- O Grafana é alcançado por um `proxy device` do Incus, não por rota do host para o mgmt. O forwarding acontece dentro do namespace do container, então o host nunca precisa de rota para `10.20.x`.

### Resultados

- **Control plane:** `ts-client` e `ts-mgmt` declarados e propagados; os dois chassis registrados no IC-SB; GENEVE de pé entre `172.18.3.175 ↔ 172.18.33.126`.
- **Separação de planes:** `lr-client-az1` aprendeu `10.10.2.0/24` **e nada de `10.20.x`**; `lr-mgmt-az1` aprendeu `10.20.2.0/24` **e nada de `10.10.x`**, simetricamente na AZ2.
- **Isolamento:** o client plane não alcança `10.20.2.10` em nenhuma AZ. **Antes** das policies do Edge Firewall, esse teste **pegou um vazamento real**.
- **Aplicação, ponta a ponta:** `GET /api/status` pelo VIP do frontend da AZ1 é respondido por `app-vm-2` **na AZ2** com banco vivo, em `≈ 45 ms`. O service VIP respondido 8/8 pelo backend da AZ2; os dois VIPs próprios 12/12; o dashboard renderiza **19 linhas das duas AZs, nenhuma em erro**.
- **Cross- vs intra-AZ no `ts-mgmt`:** RTT ao banco de **3,191 ms** da AZ1 vs **0,059 ms** da AZ2: **~54×**, medido numa execução só.
- **Norte-sul:** os três workloads alcançam a internet (HTTP 200), cada um pelo SNAT do seu plane.
- **MTU:** `-s 1414 -M do` passa, `-s 1415` falha.
- **HA da interconexão:** parar o **líder** elegeu outro em segundos; o cluster degradado 2-de-3 **ainda confirmou escrita**; o data plane não percebeu; o membro voltou limpo.
- **Idempotência:** `ic_cluster`, `central`, `chassis` e `services` reportam `changed=0`; `topology` reporta 1 (o restart deliberado).

### Decisões de design

| Decisão                                         | Razão                                                                                          | Trade-off                                            |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| OVN dirigido à mão; Incus só fornece o workload | o Incus gerencia o NB sozinho e não expõe configuração de OVN-IC                               | mais passos manuais na role `workloads`              |
| Isolamento por datapaths, não por fabrics       | é o que o desenho especifica: dois transit switches sobre um túnel                             | fronteira de roteamento, não de criptografia         |
| O banco é single-NIC                            | o isolamento não pode ser desfeito por erro de roteamento: não existe endereço para alcançá-lo | nenhum relevante, é garantia mais forte que firewall |
| Um tier de edge por célula                      | pelo desenho, e pela restrição do OVN sobre LB × DGP                                           | uma camada de roteamento a mais                      |
| VIPs por AZ, não um global                      | o desenho é simétrico: cada célula oferece o serviço localmente                                | exigiu o service VIP para o caso cross-AZ            |
| Containers, não VMs                             | hosts de 2 vCPU / 8 GB; containers exercitam o mesmo datapath GENEVE                           | isolamento menor                                     |
| App partida entre AZs                           | o fluxo sob teste vira o tráfego do próprio produto, não uma sonda sintética                   | acopla as camadas às AZs                             |
| JDK puro, sem Spring/Maven                      | containers pequenos atrás de NAT duplo; árvore de dependências é lenta e frágil                | sem ergonomia de framework                           |
| O árbitro é mínimo                              | sem chassis, sem GENEVE, só `openvswitch-common` — para não virar nó de datapath por acidente  | uma VM só para votar                                 |
