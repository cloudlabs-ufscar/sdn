
> IMPORTANTE:  Nesse estudo, utilizaremos o OpenStack Neutron como fonte. 


- Neutron é o projeto do OpenStack que gerencia serviços de rede. Ele é exposto como uma API para os usuários e serviços internos da cloud, e dessa forma os usuários podem definir a conectividade de rede na cloud para seus workloads. 

- As principais features suportadas pelo Neutron são:
	1. Switching - Usando como backend uma solução de SDN, é possível conectar os workloads em um mesmo segmento L2 (subnet)
	2. **Routing** - Usado para prover conectividade dos workloads de diferentes subnetes e com ambientes externos.
	3. **ACL** - Usado para permitir ou negar os acessos de E/S para os workloads.
	4. **Load Balancer** - Permite realizar o balanceamento de carga de serviços entre os workloads.
	5. **Conectividade externa** - Acesso a internet.

- Existem dois tipos de redes que podem ser definidas pelo Neutron:
	- Project Network - Uma subnet criada por usuários ou administradores da cloud que irá ser utilizada para conectar os workloads e que em sua maioria é privada.
	- Provider Network - Uma subnet criada somente por administradores da cloud que é utilizada para criar conectividade externa.

- Essas são as nomenclaturas utilizadas:
	- Subnet - Um bloco de endereços IP usado para conectar workloads e criar conectividade local e remota.
	- Subnet Pool - É uma maneira do Neutron escolher qual endereço de subnet possível pode ser utilizada a partir de um Pool. Pool nesse caso é uma subnet maior, por exemplo /16 e através de uma subnet pool, o usuário pode escolher subnets menores como /24. 
	- Port - Ponto de conexão de um workload em uma subnet.
	- Router - Responsável por criar conectividade entre diferentes subnets e com o provider.
	- Security group - Controla o tráfego através de ACLs
	- DHCP - Serviço de rede que gerencia o provisionamento dinâmico de IP.
	- Floating IP (FIP) - É um endereço de IP público em sua maioria que pode ser associado em um workload diretamente para que seja possível expor um serviço externamente. O endereço de FIP não é visível pelo SO do workload. É possível alterar o FIP de um workload para outro, sendo um IP "fixo" usado para a conexão externa.
	- SNAT - Para um router que esteja conectado em uma Provider, por padrão será executado o SNAT, que visa criar conectividade dos workloads conectados em subnets privadas com a Internet na direção workload -> Internet. 

- O Neutron faz o papel de CMS, executa na camada de Controller do Openstack e possui vários componentes de serviço. O `neutron-server` por exemplo é responsável em interfacear todas as chamadas de API com os outros módulos da arquitetura do Openstack que solicitam algo de rede. O Neutron se integra com N soluções de rede através do ML2, que é um framework que permite o Neutron ser híbrido. No caso do OVN, o Neutron possui o plugin ML2/OVN de integração e o principal propósito do plugin é traduzir toda a configuração lógica de rede armazenada no banco de dados do Neutron em um formato intermediário entendido pelo OVN que será o Logical Flow.

- Além de componentes nos Controller do Openstack, o Neutron possui o `metadata-agent` que está presente nos **Chassis** (Compute Nodes). Via serviço de Metadata o usuário final da Cloud pode configurar vários aspectos nas VMs: hostname, injetar chave SSH e etc. O `metadata-agent` é integrado com o OVN Southbound database para reportar alguns status.

- Existem algumas diferenças entre a integração do ML2 com o OVS e com o OVN:

|               | ML2/OVS                                                  | ML2/OVN                                                                                          |
| ------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Communication | RabbitMQ                                                 | OVSDB                                                                                            |
| Metadata      | O agente executa em conjunto com os agentes de DHCP e L3 | O agente executa no Compute Node                                                                 |
| L3            | O agente executa nos Network Nodes e Compute Nodes       | Não existe agentes, tudo é manipulado pelo OVN e programado via OpenFlow flows nos Compute Nodes |
| DHCP          | O agente executa nos Network Nodes                       | Não existe agente, o serviço é provido via OpenFlow flows nos Compute Nodes                      |
