## 1. OSI Model

 O modelo OSI é uma ideia que é mapeada da seguinte forma:

| OSI            | PDU                    | Endereçamento                            | Exemplos                           |
| -------------- | ---------------------- | ---------------------------------------- | ---------------------------------- |
| 7.Aplicação    | Data                   | Nomes/URLs, identificadores da aplicação | HTTP, DNS, SSH, DHCP               |
| 6.Apresentação | Data                   | -                                        | TLS, UTF-8, JSON                   |
| 5.Sessão       | Data                   | identificadores de sessão                | RPC, NetBIOS, mecanismos de sessão |
| 4.Transporte   | Segmento/<br>Datagrama | Porta TCP/UDP                            | TCP, UDP                           |
| 3.Rede         | Pacote                 | IP                                       | IPv4, IPv6, ICMP                   |
| 2.Enlace       | Frame/Quadro           | MAC                                      | Ethernet                           |
| 1.Física       | Bits                   | -                                        | Rádio, fibra, Ethernet PHY         |
> Legenda:
> PDU (Protocol Data Unit): Nome dado a um bloco de dados em cada camada

Encapsulamento é o mecanismo central: Cada camada trata a PDU da camada de cima como payload (parte principal da mensagem) opaco e prefixa seu próprio header:
```
[ Ethernet | IP | TCP | HTTP ...................... | FCS ]
 14 bytes    20   20    payload                       4
```

> Legenda:
> FCS (Frame Check Sequence): Campo de 4 bytes localizado no final do quadro Ethernet usado para detectar erros de dados ocorridos durante a transmissão na rede. Funciona com checksum entre o emissor dos dados e o receptor. 

Esse encapsulamento gera uma consequência importante: O Overhead se acumula, já que cada header consome bytes que não são dados úteis pra ele. Em overlay isso vira problema de MTU.

Alguns conceitos relevantes são:
- **MTU** (Maximum Transmission Unit) - É o maior payload que um frame de enlace carrega. Ethernet padrão: 1500 bytes de payload L3. O frame completo no fio é 1518 bytes (14 de header + 1500 + 4 de FCS), 1522 com uma tag VLAN.
- **MSS** (Maximum Segment Size) - Payload TCP máximo (L4). Em IPv4: `MTU - 20 (IP) - 20 (TCP) = 1460`.
- **Frame Size** - O que trafega no fio, incluindo header L2 e FCS.
- **Jumbo Frame** - MTU > 1500, tipicamente 9000. Funciona como um grande pacote ao invés de pequenos pacotes segmentados.
## 2. L1 e L2

O endereço **MAC** (Media Acces Control) é um identificador único por hardware. O Formato do frame Ethernet II é:

```
+----------+----------+-----------+---------------+-----+
| DST MAC  | SRC MAC  | EtherType | Payload       | FCS |
| 6 bytes  | 6 bytes  | 2 bytes   | 46-1500 bytes | 4   |
+----------+----------+-----------+---------------+-----+
```

- Endereço MAC - 48 bits, escrito em hex. Estrutura:
	1. Primeiros 24 bits - Identificador do fabricante (OUI)
	2. Bit I/G (bit menos significativo do primeiro octeto): 0 = unicast, 1 = multicast/broadcast
	3. Bit U/L (segundo bit menos significativo do primeiro octeto): 0 = globalmente único, 1 = administrado localmente. Endereços gerados por hypervisor ou container runtime setam esse bit.
	Exemplo:
	`02:42:ac:11:00:02` (Docker). Tem o primeiro octeto `02 = 00000010`, ou seja bit U/L ligado, bit I/G desligado: unicast localmente administrado.
	`ff:ff:ff:ff:ff:ff` tem todos os bits ligados: broadcast

- Existem três modos de entrega de frames em L2:
	- Unicast - MAC de destino específico. O switch entrega em uma porta só (se souber onde está).
	- Broadcast - Entregue em todas as portas do domínio de broadcast exceto na origem. Usado por ARP request, DHCP Discover.
	- Multicast - Bit I/G ligado, destino é um grupo. Ex.: `01:00:5e:xx:xx:xx` para IPv4 multicast, `33:33:xx:xx:xx:xx` para IPv6 multicast. O multicast sabe o grupo alvo do frame através do mapeamento do endereço IP multicast para um endereço MAC multicast específico. Sem IGMP Snopping o switch trata multicast como broadcast.

>**IGMP Snooping**: Recurso usado por switches de rede para otimizar o tráfego de dados multicast. O switch escuta as mensagens do protocolo IGMP trocadas entre roteadores e os dispositivos finais, e mapeia os interessados, descobrindo quais portas do switch querem receber um determinado conteúdo multicast. 

> ***O OVN foi desenhado para eliminar broadcast. ARP, DHCP e ND são respondidos localmente por flows no hypervisor de origem, sem tocar na rede.***

Um switch L2 opera com uma máquina simples:
	1. Frame chega na porta `P` com SRC MAC `M`.
	2. Learning: Registra na tabela CAM/MAC que `M` está acessível por `P`, com timestamp.
	3. Forwarding: Olha o DST MAC:
		- **Forwarding** - Encaminha só naquela porta mapeada na tabela
		- **Flooding** - Se não está na tabela (unknown unicast) ou é broadcast/multicast, envia em todas as portas do mesmo domínio de broadcast. Assim que o dispositivo alvo responder, aprende a porta e adiciona na tabela.
		- **Filtering** - Se o destino está na mesma porta da entrada, o frame é descartado, pois sabe que o dado já chegou ao destino. 

> **Content Addressable Memory (CAM)**: Tabela que guarda quem é quem na rede, associando o MAC Address do dispositivo à porta física do switch onde ele está conectado

Existem algumas consequências operacionais desse fluxo:
	- **Unknown unicast flooding** é tráfego desperdiçado e vazamento de dados. Em redes grandes é fonte real de problema.
	- **MAC flapping**: O mesmo MAC aparecendo alternadamente em duas portas indica loop ou VM migrada. Em log de switch é sinal de alerta.
	- **CAM table overflow**: Ataque clássico, inundar com MACs falsos até estourar a tabela, forçando o switch a floodar tudo (fail-open), o que permite sniffing. Mitigação: port security / limite de MACs por porta.

É possível definir um **domínio de broadcast**, onde existe um conjunto de portas onde um broadcast se propaga. Delimitado por um roteador ou fronteira de VLAN, então um switch com 3 VLANs tem 3 domínios de broadcast  (além de tipicamente uma sub-rede IP).
## 3. L3
### IP
Um endereço **IPv4** possui 32 bits.  A **máscara** delimita a **quantidade de bits que identificam a rede**. Então por exemplo, `/24` diz que os primeiros 24 bits identificam a rede, e os 8 bits restantes identificam o dispositivo dentro da rede. Já que um **IPv4 tem 32 bits**, é possível ter combinações como `/16`, `/8` e etc. **Quanto menor o número da máscara, maior o número de hosts**. Por exemplo, imagine o IP:
		`192.168.1.10/24`, como os primeiros 24 bits são a rede: 
		`192.168.1.X`, e como sobram 8 bits para os hosts, temos:
		2^8 = 256 endereços, portanto:
		`192.168.1.0` até `192.168.1.255`

 Existem ranges de subnets especiais que possuem papéis importantes:

| Range          | Significado                                            |
| -------------- | ------------------------------------------------------ |
| 10.0.0.0/8     | privado                                                |
| 172.16.0.0/12  | privado                                                |
| 192.168.0.0/16 | privado                                                |
| 100.64.0.0/10  | CGNAT - espaço interno de cloud                        |
| 127.0.0/8      | loopback                                               |
| 169.254.0.0/16 | link-local/APIPA, endereço de metadata usado em clouds |
| 224.0.0.0/4    | multicast                                              |
| 0.0.0.0/0      | rota default/"qualquer"                                |

Um endereço IPv6 possui 128 bits, com notação em hex dispostos em 8 grupos:
`2001:0db8:0000:0000:0000:0000:0000:0001` → `2001:db8::1` (o `::` pode aparecer uma única vez).

Diferenças entre IPv4 e IPv6:
- IPv6 substituiu brodcast por multicast. `ff02::1` = todos os nós do link, `ff02::2` = todos os roteadores.
- ARP não existe, foi substituído por **NDP** (Neighbor Discovery, sobre ICMPv6): Neighbor Solicitation / Neighbor Advertisement para resolução de endereço utilizando seu próprio IP link-local de origem para um endereço multicast, Router Solicitation / Router Advertisement para descoberta de gateway.
- Link-local obrigatório. Todo nó tem um `fe80::/10`, gerado automaticamente e funciona como origem. É sobre ele que NDP e protocolos de roteamento operam.
 - **SLAAC**: autoconfiguração via Router Advertisement, sem servidor DHCP. Flags no RA (`M` e `O`) indicam se DHCPv6 deve ser usado para endereço e/ou outras informações.
- **Prefixo padrão de LAN é /64.** Não por escassez, mas porque SLAAC depende disso. Links p2p usam /127.
- **Sem NAT por padrão**. O modelo é endereçamento global fim a fim, com firewall fazendo o papel de controle.
- **Sem fragmentação em roteador.** Só a origem fragmenta; roteadores mandam ICMPv6 Packet Too Big. Isso torna o PMTUD **obrigatório** e faz o bloqueio cego de ICMPv6 quebrar a rede.

> ***No OVN, IPv6 é muito utilizado: há ND responder nativo, RA emitido pelo logical router, DHCPv6 stateless/stateful. Tudo implementado como logical flows, sem broadcast e sem daemon por rede.***

### ARP

**ARP** (Address Resolution Protocol) faz a resolução entre IPv4 e MAC dentro de um mesmo domínio de broadcast. Funciona no seguinte fluxo:
	1. Host A quer falar com `10.0.0.5`, mesma sub-rede, porém não tem o MAC
	2. Envia ARP Request em broadcast
	3. Host B responde com ARP Reply em unicast
	4. A guarda em cache (`ip neigh`), com estados: REACHABLE, STALE, DELAY, PROBE, FAILED.

Se o destino está fora da sub-rede, o host não faz ARP do destino. Ele faz ARP do gateway e envia o frame com o MAC do gateway e IP do destino final. Essa separação é o conceito de roteamento.

### ICMP

**ICMP** (Internet Control Message Protocol) é o canal de sinalização do IPv4. Os tipos que importam:

| Tipo/Código | Nome                               | Utilidade                              |
| ----------- | ---------------------------------- | -------------------------------------- |
| 8/0         | Echo Request/Reply                 | ping                                   |
| 11          | Time Exceeded                      | TTL zerado (base do traceroute)        |
| 3/0, 3/1    | Destination Unreachable (net/host) | -                                      |
| 3/3         | Port Unreachable                   | resposta a UDP em porta fechada        |
| 3/4         | Fragmentation Needed com DF set    | base do PMTUD                          |
| 5           | Redirect                           | gateway avisando que há caminho melhor |
 > **PMTUD (Path MTU Discovery)** : O host marca DF (Don't Fragment) e envia pacotes de tamanho do MTU local. Se um roteador no caminho tem MTU menor, ele descarta e responde ICMP tipo 3 código 4 informando o MTU permitido. O host reduz e reenvia.


### NAT

**NAT** (Network Address Translation) é responsável por converter IP privados de uma rede interna em um único IP público para acessar a internet. Possui alguns tipos:
- **SNAT** (Source NAT) - Reescreve o IP de origem. Pode ser usado por hosts privados saindo para a internet. Quando muitos hosts compartilham um IP público, é preciso reescrever também a porta de origem: isso é **PAT / NAT overload / masquerade**
- **DNAT** (Destination NAT) - Reescreve o IP de destino. Pode ser usado no port forwarding, publicar um serviço interno ou por load balancer
- **1:1 NAT / floating IP** — um IP público mapeado a um privado, com DNAT na entrada e SNAT na saída. É exatamente o `dnat_and_snat` do OVN.

**Conntrack** é o subsistema Kernel responsável por **acompanhar o estado de todas as conexões de rede** que passam pela máquina. É o que torna o NAT possível,  já que o Conntrack é uma tabela de fluxos com estados (NEW, ESTABLISHED, RELATED, INVALID). NAT só funciona porque o kernel lembra da tradução para reverter no pacote de resposta. Isso também é o que dá _stateful firewall_: permitir ESTABLISHED/RELATED e negar NEW de fora.

> ***No OVN, NAT é declarado no `Logical_Router`, e implementado por logical flows com conntrack no datapath do OVS.***


### VRF

VRF (Virtual Routing and Forwarding) é uma tecnologia de redes que permite a um único roteador ou switch de L3 manter múltiplas tabelas de roteamento independente ao mesmo tempo sem gerar conflitos. Cada VRF tem seu próprio espaço de endereços, podendo inclusive usar os mesmos prefixos que outra VRF sem conflito. É a virtualização de L3, assim como VLAN é a virtualização de L2.

**Route leaking**: Importar seletivamente rotas de uma VRF para outra. Se duas VRFs utilizam faixas de endereçamento IP idênticas (endereços sobrepostos ou overlapping IPs) é necessário um mecanismo para resolver o conflito. A tabela de roteamento global ou de destino não saberá para onde encaminhar o pacote, pois haverá prefixos idênticos apontando para destinos diferentes. É possível lidar com isso principalmente com o uso de NAT, que traduz os endereços da VRF de origem para um IP exclusivo antes de injetar na outra VRF.

> ***Um `Logical_Router` no OVN é conceitualmente uma VRF. Dois routers lógicos de tenants diferentes são tabelas de roteamento completamente independentes, podendo usar as mesmas faixas privadas. O route leaking entre eles se faz conectando ambos a um logical switch comum, com rotas estáticas, ou entre availability zones (via OVN-IC e transit switch)***

## 4. L4
### TCP

**TCP** (Transmission Control Protocol) é o protocolo que garante que os dados sejam transmitidos de um dispositivo para outro de forma segura, confiável e na ordem correta. Seu Header possui 20 bytes: Portas origem/destino, sequence number, acknowledgment number, data offset, flags, windows, checksum e urgent pointer. 

O handk-shake entre cliente e servidor é feito da seguinte forma:
```
Cliente                         Servidor
   |  SYN, seq=x                   |
   |------------------------------>|
   |  SYN-ACK, seq=y, ack=x+1      |
   |<------------------------------|
   |  ACK, ack=y+1                 |
   |------------------------------>|
```

> Legenda:
> - SYN (Synchronize): O cliente envia um pacote com a flag SYN para o servidor com o número de sequência.
> - SYN-ACK (Synchronize-Acknowledge): O servidor responde com um pacote contendo SYN e ACK, que concorda com o recebimento do pedido, e informa o número de sequência.
> - ACK (Acknowledge): O cliente envia de volta um pacote ACK confirmando a resposta, a partir daí a conexão está aberta. Retorna com a sequence do servidor incrementado em uma unidade.

O encerramento da conexão é feito da seguinte forma: FIN → ACK → FIN → ACK (quatro vias, pois cada direção fecha independentemente. O lado que fecha primeiro entra em **TIME_WAIT** por 2×MSL (60s no Linux), para absorver pacotes atrasados e garantir a entrega do último ACK.

### UDP

**UDP** (User Datagram Protocol) é um protocolo de comunicação simples do L4. Possui um header de 8 bytes (portas, tamanho, checksum). Sem conexão, sem ordenação, sem retransmissão, sem controle de congestionamento. Vantagens: latência mínima, sem estado, suporta multicast/broadcast, e deixa a aplicação decidir a semântica. Usos: DNS, DHCP, NTP, SNMP, RTP (voz/vídeo), VXLAN/Geneve (encapsulamento), QUIC.

**QUIC** (Quick UDP Internet Connections) é um **protocolo de camada de transporte** moderno criado para substituir o TCP, por realizar o transporte sobre UDP e reimplementando confiabilidade, controle de congestionamento e criptografia em espaço de usuário.
## 5. Outros mecanismos importantes
### Sockets

Um **socket** é um ponto final de comunicação que permite a troca de dados entre dois processos, seja no mesmo computador ou em máquinas diferentes através de uma rede. Funciona como um endereço IP combinado com um número de porta. Permite que aplicações como navegadores e servidores web conversem entre si usando protocolos como TCP ou UDP.

Uma conexão é identificada unicamente pela **5-tupla**: `(protocolo, IP origem, porta origem, IP destino, porta destino)`. É a chave de conntrack, de hashing ECMP, de flows do OVS e de regras de load balancer. 

### DHCP

**DHCP** (Dynamic Host Configuration Protocol) é o mecanismo pelo qual uma máquina que acabou de entrar em uma rede consegue descobrir/configurar seu próprio endereço IP e outras informações de rede. Como a máquina ainda não possui IP associado, a comunicação com o servidor é feita utilizando MAC Address. O fluxo DHCP básico é **DORA**:
	  1. `DHCPDISCOVER` - O pacote procurando se existe algum servidor DHCP é enviado por broadcast na rede local.
	  2. `DHCPOFFER` - Um servidor recebe o Discover e responde com as informações disponíveis, sendo elas IP, máscara, gateway, DNS e lease.
	  3. `DHCPREQUEST` - O cliente escolhe a oferta pelo servidor.
	  4. `DHCPACK` - O servidor envia as configurações para a máquina.

> ***No OVN não existe servidor DHCP. O `Logical_Switch_Port` tem `dhcpv4_options` apontando para um registro com as opções; o `ovn-northd` gera logical flows que respondem ao Discover/Request diretamente no hipervisor de origem, com a ação `put_dhcp_opts`. O broadcast nunca sai do host. Não há servidor para falhar, esse é um dos exemplos mais claros de "serviço de rede virou tabela de fluxos."***

### DNS

**DNS** (Domain Name System) é um sistema responsável por traduzir nomes de sites em endereços IP. Existem três tipos de servidor DNS:
- **Recursivo/resolver**: O que o cliente consulta; percorre a hierarquia por ele e faz cache.
- **Autoritativo**: Detém os dados de uma zona; responde apenas pelo que é seu.
- **Forwarder**: Repassa a outro recursivo.
Por exemplo:
- **Resolução de `www.exemplo.com.br`:** 
	1. Resolver consulta a raiz → recebe referral para os servidores de `.br` 
	2. Consulta `.br` → referral para `exemplo.com.br`
	3. consulta o autoritativo → resposta autoritativa. Depois tudo é cacheado conforme o TTL de cada registro.

**TTL** (Time to Live) é um mecanismo que limita o tempo de existência de um pacote de dados em uma rede IP, evitando que ele fique preso em um loop infinito.
### TLS e HTTP

O **HTTP** (Hypertext Transfer Protocol) é o protocolo da camada de aplicação usado para transmitir dados e páginas web na internet. Existem alguns tipos de protocolo HTTP:
- **HTTP/1.1** - Texto, uma requisição por conexão de cada vez.
- **HTTP/2** - Binário, multiplexação de streams sobre uma conexão TCP, compressão de headers (HPACK), server push (obsoleto na prática). Sofre **head-of-line blocking no TCP**: uma perda trava todos os streams.
- **HTTP/3** - sobre QUIC;  handshake mais rápido, migração de conexão.

O **HTTPS** (HyperText Transfer Protocol Secure) é a versão segura do protocolo HTTP, responsável por criptografar a comunicação entre o seu navegador e o servidor de um site. Utiliza o TLS como forma de proteção das conexões.

**TLS** (Transport Layer Security) é um protocolo de segurança criptográfico usado para proteger dados transmitidos em redes de computadores, como a internet. Susbtitui o antigo **SSL** (Secure Sockets Layer). O TLS realiza um handshake entre cliente e servidor para garantir a segurança do transporte do pacote.

O **SNI** (Server Name Indication) é uma extensão do protocolo TLS que envia o nome do host (domínio) desejado logo no início da conexão segura. É  o que permite virtual hosting em HTTPS e o que permite um load balancer L7 rotear por nome sem descriptografar.
### Load Balancing

O load balance é uma técnica que distribui o tráfego de rede ou de aplicações entre vários servidores para otimizar o desempenho, evitar sobrecargas e garantir alta disponibilidade. Atua em dois layers:
- **L4 (transporte)**: Decide pela 5-tupla (TCP dst), sem olhar o payload. Rápido, barato, funciona com qualquer protocolo. É o que fazem IPVS, o LB do OVN, e o `kube-proxy`.
- **L7 (aplicação)**: Lê requisições HTTP, roteia por path/host/header, faz retry, reescrita, TLS termination. Mais caro, muito mais flexível. HAProxy, Envoy, NGINX.

O **VIP** (Virtual IP) do Load Balancer é basicamente o IP que o cliente enxerga como sendo o endereço do serviço. Não é necessariamente o IP real de uma VM ou de uma interface física.

O LB possui alguns modos de operação: 
- **Proxy / NAT mode**: O LB reescreve destino (e geralmente origem). Simples; o backend vê o IP do LB, exigindo `X-Forwarded-For` ou PROXY protocol para preservar o IP do cliente. O tráfego de volta passa pelo LB.
- **DSR (Direct Server Return)**: o LB só reescreve o MAC de destino; o backend responde direto ao cliente, com o VIP configurado em loopback. Elimina o LB do caminho de retorno, o que importa quando a resposta é muito maior que a requisição (vídeo, download). Exige que os backends estejam no mesmo L2 e uma configuração de ARP cuidadosa (`arp_ignore`/`arp_announce`).
- **Maglev / consistent hashing**: hashing que minimiza remapeamento quando o conjunto de backends muda, preservando conexões existentes. Essencial em LB distribuído sem estado compartilhado.

O LB possui o mecanismo de **Health Check**, que possui dois estados:
- Ativo - O LB sonda: TCP connect, HTTP GET em `/healthz`
- Passivo - Observa falhas reais

O LB calcula um hash baseado no IP do cliente. Por exemplo:

```
Cliente A → Web1
Cliente B → Web3
Cliente C → Web2
```

O mesmo cliente tende a ser direcionado ao mesmo backend enquanto a configuração permanecer adequada. Isso pode ser usado para fornecer uma forma de **session persistence**.

Um LB pode escolher um backend utilizando diversos algoritmos:
- Round Robin - Método simples que distribui as solicitações dos clientes de forma sequencial e circular por uma lista de servidores.
- Weighted Round Robin - Cada servidor possui um peso. Útil quando os servidores têm capacidades diferentes. 
- Least Connections - O LB observa quantas conexões cada backend possui e redistribui novas conexões 
- Weighted Least Connections - Combina número de conexões e capacidade/peso do servidor. É útil quando os backends possuem capacidades diferentes.


> ***No OVN, o load balancer é uma tabela no NB DB associando VIP:porta a uma lista de backends, aplicada a um logical switch ou logical router. A implementação é feita com `ct_lb`,  o datapath usa conntrack para escolher um backend na primeira conexão e manter a afinidade nas seguintes. Como isso roda em cada hipervisor, o balanceamento é distribuído: não existe um appliance central por onde todo o tráfego passe. É a mesma ideia do `kube-proxy`/IPVS, implementada no datapath do OVS.***

## 6. Network, Subnet e AZs

- **Network** é um conjunto de dispositivos que conseguem se comunicar através de alguma infraestrutura e regras de encaminhamento.
- **Zonas de Disponibilidade** (AZ) seria análogo à uma Network, com Switches, Routers, Servers, porém mais voltada ao conceito de cloud.
- **Subnet** é um conceito especificamente relacionado ao endereçamento IP. É a faixa de IP disponível para dispositivos.
